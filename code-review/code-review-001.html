World Model Judge — Code Review 001

The first code review this project has run, after nine design-review rounds and two completed build phases (worlds + first chart). Six defect-class panels scanned every file under src/wmj/ and its paired tests. The codebase is fundamentally sound — physics, determinism, and contracts are correct — but this pass found a specific, recurring pattern: the spec-reconciliation work done earlier in this same session (design-review-009's gap closures) did not fully propagate to every sibling location it touched, and several fail-loud guards this project's own conventions require have never been proven to actually fire.

Verdict

Verdict
Merge with caveats

First-ever code review for this project. No Critical findings survive triage — Panel F (stub detection) flagged five functions under its mechanical single-return-statement heuristic, but all five are legitimate, fully-implemented code (a documented no-op, a boundary comparison, a tuple builder, two validated-singleton accessors), not incomplete placeholders; recommended disposition is DISMISS as heuristic false positives. Eight Important findings remain, none of which represent a live functional break: three trace to this session's own design-review-009 reconciliation pass not fully propagating (a stale docstring, a spec sentence missing the same fix just applied to its sibling, three new test-case IDs never wired into test names, a full-scale gate missing the two-sided assertion its fast counterpart has); a systematic gap in this project's own phantom-gate discipline (several fail-loud guards have no test proving they fire); one dead-by-construction field that can never be observed False by any caller; one unguarded division reachable from a bare CLI integer; and one defect two panels found independently (frozen dataclasses handing back shared, uncopied numpy arrays). Accepted risk if merged as-is: none of these affect today's numbers or verdicts — they are verification-completeness and documentation-accuracy gaps, exactly the class of thing a first code review exists to catch before Phase 3 raises the stakes.

Important Findings

I1 — This session's own spec-reconciliation pass left three sibling defects of the same class uncorrected
specs/cross-cutting.md item 10 (the new REPORTING_ALLOWLIST gate, added in this session) omits `__future__` from its allowlist prose — the exact defect just corrected for item 9's models-allowlist sentence in the same commit, even though every reporting module carries `from __future__ import annotations` and the code only passes because `ALWAYS_ALLOWED` is silently unioned in. Separately, this session minted three new test-case IDs (TC-NF6-10, TC-NF6-11, TC-MU2-03) but never wired any of them into the actual test function names or docstrings in tests/gates/test_import_graph.py or tests/unit/models/test_baselines.py — breaking this project's own stated convention that requirement/case IDs appear in gate-test names, exactly where a brand-new ID was introduced. And tests/gates/test_benchmark_full_scale.py's full-scale TC-WD4-01 gate still asserts only the upper bound (`ratio < 10.0`); the two-sided fix applied to the fast test (`0.1 < ratio < 10.0`) never propagated to its full-scale counterpart. Fix: add `__future__` to item 10's stated set; rename or add the three ID references into the relevant test names; add the lower-bound assertion to the full-scale gate.
I2 — baselines.py's own module docstring still describes ddof as an open backlog item the spec has since settled
The docstring says: 'ADR-M2 does not pin ddof; the choice is recorded as backlog candidate A8 because it changes bytes.' specs/models.md ADR-M2 now reads 'ddof=1 (sample standard deviation), pinned for both fits (corrected design-review-009 A8/C1)' — an Accepted decision, not an open question. The runtime code is correct; only the code's own contract commentary is stale, and a maintainer reading only this docstring could believe ddof is still a renderer's-discretion choice and 'fix' it away from the pinned value, silently changing every downstream CRPS/skill/Verdict byte. Fix: update the docstring to state ddof=1 as the spec-pinned decision, citing ADR-M2 directly, dropping the backlog framing.
I3 — assert_single_threaded(), the actual verifier ADR-002 rule 1 calls for, is dead code at the real entry points
Only ensure_single_threaded() (the setter) is called, in __main__.py, before cli is imported. assert_single_threaded() (the verifier) is invoked nowhere except its own unit test. Every unit test that imports wmj.harness.cli.main directly bypasses the thread guard entirely — numpy/BLAS get whatever thread count is ambient in the pytest process, with nothing asserting or reporting it. The one place this ordering claim actually matters today (TC-NF1-01's byte-identity gate) is unaffected — it launches genuinely separate OS processes via subprocess.run, which does go through __main__.py in the correct order. Fix: call assert_single_threaded() at the top of cli.main() (or the top of write_skeleton_report()/run_chart_preview()), not only ensure_single_threaded() in __main__.py, so the invariant is enforced at every entry point, not only the one the byte-identity gate happens to use.
I4 — the per-region drift artefact's within_bound field is dead-by-construction — it can never be observed False by any caller
assert_drift_within_bound() raises before the line that would ever set within_bound to False is reached, so build_divergence_artefact's drift_per_region entries hardcode within_bound: True unconditionally, and the top-level all(...) aggregate is equally tautological. Existing tests only assert the value is True, which is guaranteed by construction, not by measurement. A future consumer (reporting, judge) that branches on drift['within_bound'] believing it carries real per-region information will always take the true branch. Fix: either drop the field (the raise already is the gate) or restructure so the boolean is genuinely derived from a stored comparison rather than a literal; if kept, comment explicitly that it is always True by construction.
I5 — a systematic gap in this project's own phantom-gate discipline: several fail-loud guards have no test proving they fire
reporting/horizon_plot.py's _validate function has several compound `or` guards where only one disjunct is ever exercised by the parametrized test suite (the dt-guard's negative/NaN/wrong-type cases, the non-list/non-dict type-check halves, the n<2 case). models/base.py's SeedSource.rng() SeedKeyError guard (fires when my_name is None) is never exercised by any test. reporting/captions.py's CaptionLengthError (the RP-5 three-sentence limit) is never raised in any test — write_caption is only ever called with a 2-sentence string. harness/cli.py's argparse fallthrough ('no runnable command selected') — the path a user hits by typing the most obvious invocation, `wmj run` without `--skeleton` — is never exercised. Each is a genuine phantom gate: the raise exists in the code but nothing proves it can actually fire for that specific condition, against this project's own explicitly stated convention that every fail-loud mechanism needs a negative/phantom-gate test. Fix: add the missing negative-case tests for each guard listed.
I6 — an unguarded ZeroDivisionError is reachable from a bare CLI integer, violating the project's own Error-Handling convention
one_step_skill_persistence_vs_linear's mean_crps divides by len(starts) with no guard; n_trials is a bare CLI integer (--n-trials) passed straight through. --n-trials 0 reaches this division and produces an unguarded, contextless ZeroDivisionError — naming nothing about which requirement's gate fired, contrary to this project's own Error-Handling rule that every exception message names what failed and why. Fix: validate n_trials >= 1 (and n_starts >= 1, horizon >= 1) at the top of run_chart_preview/build_lv_persistence_error_vs_horizon, raising a named WmjError subclass with a requirement reference, rather than letting a bare ZeroDivisionError reach the user.
I7 — frozen dataclasses hand back shared, uncopied numpy arrays across calls (found independently by two panels)
Prediction, RegionSpec, and WorldContext are declared frozen=True, but frozen=True only blocks field reassignment — it does nothing to the contents of a numpy array a field holds. PersistenceModel/LinearModel hand back the identical self._spread array object from every single predict() call rather than a copy; lv._REGION_SPEC and WORLD.scale are built once at import time and returned by reference, uncopied, for the rest of the process. No current call site does an in-place write into any of these (every consumer uses / not /=), so there is no live bug today — but a single future stray in-place op anywhere downstream would silently corrupt a shared singleton for every unrelated call for the rest of the process, in a project whose entire credibility claim is that no such hidden cross-call dependency exists. Fix: either .copy() the arrays at construction, or enforce read-only via array.setflags(write=False) on the module-level singletons and on self._spread in the baselines, so a future in-place mutation raises immediately instead of silently propagating.
I8 — the drift normaliser's span<=0 fallback silently changes what the bound measures, with no error, log, or test
rel_drift_max = max_abs_drift / span if span > 0.0 else max_abs_drift silently changes units — from 'relative to the invariant's range' to 'absolute drift' — whenever a region's conserved-quantity range collapses to a single value, with no error, no log, and no test ever exercising this branch. Currently unreachable for LV/pendulum's declared boxes (both have real non-zero conserved-quantity ranges, independently verified), but nothing prevents a future world's box from hitting it silently, changing what the 1e-6 bound means without disclosure. Fix: raise a dedicated error when span <= 0.0 for a region declared to have a genuine invariant, matching this project's own fail-loudly doctrine, or explicitly document the fallback's unit change in the artefact schema.
