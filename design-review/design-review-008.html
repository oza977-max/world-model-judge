Critical Findings

C1 — os.environ's dunder access bypasses the v1.7 mutate-in-place guard; Python resolves special methods against the type, not the instance

Panel: E-calibrated (4/10), executed.

Files: specs/cross-cutting.md ADR-002 rule 3, specs/judge.md §4.

Executed: after installing the guard exactly as specified (os.environ.get = raise, and "the mapping dunders"), os.environ.get('HOME') raises correctly, but os.environ['HOME'], 'HOME' in os.environ, and dict(os.environ) all leak the real value. Root cause: CPython resolves obj[x], x in obj, dict(obj) against the type (os._Environ), never the instance __dict__, for any new-style class — a language rule, not an evasion. Setting real_environ.__getitem__ = raise on the instance is silently ignored. Patching os._Environ (the class) instead of the instance does work (confirmed). os.environ["X"] and dict(os.environ) are arguably the more idiomatic way to read env vars than .get(). Consequence, and why this compounds: env vars are typically stable within one developer's shell across all ten TC-NF1-01 runs, so byte-identity would not catch this either, while a different machine's $HOME/$LANG/$PATH would — exactly the cross-machine break NF-1 exists to prevent. Fix (verified): patch os._Environ's class-level dunders, not the instance.

C2 — numpy.datetime64 cannot be mutated in place at all; the only working mechanism is a rebind, contradicting the spec's own uniformity claim and reopening a known escape class

Panel: E-calibrated (4/10), executed.

Files: specs/cross-cutting.md ADR-002 rule 3, specs/judge.md §4.

setattr(numpy.datetime64, '__new__', raise) → TypeError: cannot set '__new__' attribute of immutable type 'numpy.datetime64'. The spec's umbrella sentence ("mutates the one real shared object... in place... never a swap") is claimed to cover all five guard classes including this one, but it is physically impossible for numpy.datetime64. The only implementation is numpy.datetime64 = wrapper at the module level — a rebind. Executed: a value captured before the harness installs (from numpy import datetime64 as captured) bypasses the rebind cleanly and reads the real wall clock. This is exactly the pre-capture pattern already found and fixed for os.environ in v1.7 — reintroduced here, undisclosed, because the fix pattern was never generalized to a type that structurally can't take it. TC-JU12-03's own phantom-gate case happens to still pass under a rebind (it does a fresh module-attribute lookup), so it doesn't catch this gap — meaning the test proves less than the surrounding prose claims. Needs an honest disclosure (the residual list should name this) or an out-of-process mechanism for this one capability specifically.

C3 — numpy.random's private submodules hold separate bindings the module-level patch never touches; TC-JU12-04's disclosed residual is factually wrong about its own example

Panel: E-blind (6.5/10), executed — the most consequential single finding of the round.

Files: specs/cross-cutting.md ADR-002 rule 3, specs/judge.md §4, test-cases/test-cases.md TC-JU12-04.

TC-JU12-04's disclosed residual gives numpy.random.Generator(numpy.random.PCG64()) — an unseeded draw reaching getrandom() — as an example of an uncatchable escape, reasoning that Generator.__init__ is an immutable C type. Executed: with the harness built exactly as specified (all 63 public numpy.random names patched at module level, confirmed to include PCG64, Generator, SeedSequence), the disclosed example is actually caught — PCG64() construction trips the guard on the patched name, Generator.__init__ being unpatchable is true but irrelevant. The real, undisclosed escape is a plain import: import numpy.random._pcg64 as _p; import numpy.random._generator as _g; _g.Generator(_p.PCG64()) — confirmed to bypass the guard entirely. Root cause: PCG64.__module__ == 'numpy.random._pcg64'; these submodules are already resident in sys.modules (numpy's own __init__.py imports from them), and rebinding numpy.random.PCG64 changes only the top package's namespace entry, not the submodule's own binding of the same class object. This is not ctypes, not reflection, not a raw syscall — it is an ordinary import of an already-loaded module, exactly the rebind-vs-mutate-in-place defeat this document has now found and fixed twice for other capabilities (os in Round 6, os.environ in Round 7/8 — C1 above). Unlike ctypes/getrandom, this route is closable by the same in-process technique already used elsewhere (patch numpy.random._pcg64.PCG64, numpy.random._generator.Generator, numpy.random.bit_generator.SeedSequence, numpy.random._mt19937, etc. directly) — it does not belong in the "no in-process control could stop it anyway" bucket the disclosure invokes. The disclosure needs rewriting, and the harness needs the submodule-level patches added.

C4 — ADR-004's pseudocode does not typecheck against the registry contract it cites; executed, raises AttributeError

Panels: B-calibrated (5/10 I2), C-calibrated (4/10 finding not separately numbered but confirmed), D-calibrated (4/10 C1), D-blind (6/10 finding 1), F2-calibrated (5/10 C2) — five independent confirmations, two by direct execution.

Files: specs/cross-cutting.md ADR-004; specs/models.md ADR-M1.

all_models() -> dict[str, Factory] (models.md, pinned). ADR-004 writes for model in all_models(): m = model.factory(ctx, seeds, train). Executed: default dict iteration yields keys (strings) → AttributeError: 'str' object has no attribute 'factory'; fixing to .values() still fails the same way because Factory is the callable, not an object with a .factory method → AttributeError: 'function' object has no attribute 'factory'. The correct line is for name, factory in all_models().items(): m = factory(ctx, seeds, train). ADR-004 frames itself as "an explicit algorithm so the assembly is buildable without a builder inventing it" — execution shows invention is required on line one of the loop body.

C5 — Baselines sort last in all_models() but assemble_judge_input needs them on the first iteration; no pre-pass exists

Panels: C-calibrated (4/10 I-1), D-calibrated (4/10 finding not separately numbered), D-blind (6/10 C1), F2-calibrated (5/10, confirmed via independent sorted() computation) — four independent confirmations, all computing the same sorted order.

Files: specs/cross-cutting.md ADR-004; specs/models.md ADR-M1.

sorted(['persistence','linear','direct','ensemble','fx-overconfident','fx-honest-rough','fx-brittle']) → ['direct', 'ensemble', 'fx-brittle', 'fx-honest-rough', 'fx-overconfident', 'linear', 'persistence'] (independently computed by four panels, identical result). direct is processed first; linear/persistence sort last. assemble_judge_input(world, region, preds, spreads, outs, baselines[world][region]) is called on the very first inner iteration and needs baseline predictions that, under the single uniform pass ADR-004 describes, do not yet exist. No pre-pass is shown anywhere. As pinned, the loop crashes on direct's first region for every world.

C6 — ADR-004's "one region per JudgeInput" contradicts the multi-region region_labels design stable since Round 3

Panels: C-calibrated (4/10 C-1), B-calibrated (5/10 I3, same tension flagged) — the deepest finding of the round.

Files: specs/cross-cutting.md ADR-004; specs/judge.md §4; specs/models.md §5.

ADR-004 states: "A JudgeInput carries exactly one region's trials... The judge does not receive multiple regions in one call." But judge §4 justifies region_labels's per-trial {region_name, axis} shape (over a bare boolean) specifically because "a boolean in/out flag alone can't do that once a world declares more than one out-region" — i.e., because one call must be able to carry multiple, distinct regions. models §5's own worked example shows a batch mixing "training" and "out-high-amplitude" trials in one array, calling this correction out by name (design-review-003). These are two incompatible input shapes for the same type, stated in the same document set. ADR-004 was written to close the standing orchestration gap; instead it opened a new, unreconciled contradiction with a load-bearing design element several rounds older than itself. This needs an actual decision, not a patch: either ADR-004 is wrong and JudgeInput should carry all of a world's regions per model (matching the existing region_labels rationale, and requiring only that the harness assemble one multi-region call per model instead of the harness collating N single-region Verdicts afterward), or region_labels' rationale needs correcting and the multi-region example in models §5 needs to go. The former is very likely correct — it also resolves C7 below for free, since there is then only one Verdict per (model, world), matching every downstream consumer.

The envelopes = [JudgedResult(...) ...] line that would need to perform this merge is itself elided with .... This is resolved automatically if C6 is fixed the recommended way.

C8 — run-manifest.json/out/verdicts/ ownership is contradicted across three documents, one of them contradicting itself

C9 — TC-NF1-01, the backstop the reframed purity claim depends on, may itself be a phantom gate — no separate-process requirement, unlike its own siblings

Panel: F1-blind (7/10), executed.

Files: test-cases/test-cases.md TC-NF1-01; requirements/requirements.md NF-1.

TC-NF1-01's Given/When/Then never says "separate processes" — unlike TC-WD7-01 ("in two separate processes") and TC-RP7-02 ("two separate process invocations"), both written by the same document. NF-1 itself demands byte-identity "across runs, across processes, and across machines." Executed: a stand-in judge component with a lazily-initialized, process-global cache filled from an unseeded Generator(PCG64()) on first use passes ten in-process "consecutive runs" every time (each process's ten calls are internally identical, since the cache fills once and is reused) while the underlying value differs freely across three fresh processes. This is exactly the accidental-impurity class C1/C2/C3 above (and Round 7's original ctypes/getrandom disclosure) are counting on this gate to catch. If TC-NF1-01 is built exactly as worded, it would not catch it. Needs the same "separate processes" language its siblings already carry.

Important Findings

I1 — models→judge and models→reporting imports are completely ungated, and — unlike every other residual in this project — undisclosed

Panel: F2-blind (6/10), executed.

The spec's own enumeration of banned models-outbound imports covers exactly two targets (wmj.worlds, wmj.harness). Executed: a fabricated wmj/models/* file importing wmj.judge.verdict or wmj.reporting.charts passes both existing gates with zero flagged violations. Unlike the harness/worlds gaps (both found and fixed across two rounds, each time disclosed as the finding that motivated the fix), this asymmetry is not named anywhere as a residual — a break in the project's otherwise consistent "name the gap" discipline.

I2 — Worlds have no registry/discovery mechanism; adding a world is not the low-touch scenario adding a model is

Panel: F2-blind (6/10).

worlds in ADR-004's loop is a hardcoded literal set with no all_worlds()/pkgutil equivalent anywhere (grepped, zero hits). Not a broken promise — MU-9 is worded model-scoped only — but a real asymmetry worth naming given the project's own reason for having two worlds (CLAUDE.md: "stops the judge being secretly specialised to one world").

I3 — MU-5's matching-margin mechanism is hardcoded to the two named models; ADR-M5 implies it generalizes to any newly-registered unrigged model, but no mechanism does

Panel: F2-blind (6/10).

ADR-M3 specifies the margin check as a fixed pairwise comparison between "the two models" (direct, ensemble) by name; ADR-M5's MU-9 disclosure says naming a third unrigged model in recipe.md is what makes it "compared under MU-5's margin" — no such N-model generalization is specified anywhere.

I4 — TC-MU9-01(c)'s joined-name import check would false-positive on the exact import its own carve-out permits

Panel: F2-calibrated (5/10 I1), executed.

The pinned join rule's worked examples only cover from wmj.models import X shapes; the harness's actual, sanctioned import — from wmj.models.base import SeedSource — joins to wmj.models.base.SeedSource, not literally in the allowed set {wmj.models.registry, wmj.models.base}. Executed: a literal implementation blocks this legitimate import. No fixture exercises this shape. Needs an explicit rule for "module already denotes a full submodule path."

I5 — component_key has a second, sibling non-injectivity gap the colon-fix didn't address: type-representation collision

Panel: F1-calibrated (6.5/10), executed.

component_key(1, "a") == component_key("1", "a") and component_key("ensemble", 3) == component_key("ensemble", "3") — str(p) collapses an int and its decimal string to the same joined text. The spec itself uses both call shapes (seeds.rng("member", k, "weights") with k an int) with no pinned rule on caller type discipline. Same disease as the colon bug (Round 7's I4), one coercion step over. Fix: reject non-str parts at construction, same pattern as the colon guard.

I6 — check_prereg's first-added-commit resolution is ambiguous under delete-then-re-add; correct only if implemented with the right git ordering, which the spec doesn't pin

Panel: D-calibrated (4/10 I2), executed; partially reconciled by E-blind (6.5/10), which confirmed tail -1/oldest-first resolution works correctly against the same scenario.

git log --diff-filter=A can return multiple add-events for one path (delete, then honestly re-add with tuned content); the spec never states whether to take the newest or oldest. Taking the newest (a natural "first line of output" reading) selects the re-add commit and silently passes the gaming scenario the case exists to catch. E-blind confirms the correct choice (oldest/tail -1) closes it. Needs the ordering pinned explicitly in the spec text, not left to an implementer's luck.

I7 — The canonical serializer's "floats via Python's repr" rule is a stated policy, not a pinned mechanism, and breaks under NumPy ≥2.0 — the exact version this review's own environment runs

Panel: F1-blind (7/10), executed.

repr(np.float64(0.031)) under NumPy 2.x returns np.float64(0.031), not valid JSON (NEP 51). json.dumps stays safe only because its C encoder never calls __repr__ on a float — an implementation fact never stated. TC-NF3-01 checks package names only, not the <2.0 version ceiling. A natural hand-rolled implementation of "rendered with repr" breaks outright on the environment this review ran in. Needs the mechanism pinned (.tolist() before serialization, json.dumps as the sole float path) or the version ceiling gate-enforced.

I8 — envelope.meta's field count is stated inconsistently: judge §5 pins four fields, reporting §6 says three, silently dropping thresholds_file

Panel: B-calibrated (5/10 I1).

judge §5's example carries {seed, platform, prereg_commit, thresholds_file} — four fields. reporting §6 states "envelope.meta's three fields plus package_versions" and reporting's own run-manifest layout comment omits thresholds_file. No rationale given for dropping it, unlike package_versions's deliberate new sourcing.

I9 — TC-JU12-04 is wired at P4-C06 but needs results.html, which doesn't exist until P5-C04

Panel: D-calibrated (4/10 I1).

TC-JU12-04's three-way consistency check needs judge §4, cross-cutting ADR-002 rule 3, and the results.html methods note — the third doesn't exist five chunks earlier at P4-C06, and no scope split (unlike TC-WD3-01/TC-RP2-01/TC-JU3-01's careful partial/full scoping elsewhere in the same guide) is given.

I10 — os's guarded-function list is illustrative, not exhaustive; os.fork/os.exec*/os.posix_spawn bypass the subprocess guard entirely

Panel: E-blind (6.5/10), executed.

The spec's own list ("system, getcwd, getenv, urandom, getpid, listdir, stat, …") never names process-creation primitives that reach the same class of effect os.system is guarded against, and subprocess being guarded doesn't cover them. A plain build-checklist gap, not a structural defeat, but exactly the kind of enumeration omission four prior rounds already proved this project's lists are prone to.

Recommended Disposition

Cluster 1 — Mechanical, execution-verified fixes available now (recommend fix)

C10 (wire the four cases, fix the misattribution, add the v1.7 changelog row), I4 through I10, and the minors. Each has a demonstrated correct implementation already found by the panel that flagged it.

Cluster 2 — The purity hardening needs a second, more careful pass (recommend fix, same execution discipline, generalizing the pattern this time)

C1 (patch os._Environ's class, not the instance), C2 (disclose the numpy.datetime64 rebind honestly, or find a class-level alternative), C3 (patch the numpy.random submodules directly, rewrite the TC-JU12-04 disclosure to be factually accurate), I10 (extend the os guard list). C9 (add "separate processes" to TC-NF1-01) is cheap and should travel with this cluster since it's the backstop these fixes lean on.

Cluster 3 — ADR-004 needs to be rethought before it's patched (recommend: decide the partitioning question first, then rewrite)

C6 is the fork — likely resolved by making JudgeInput carry all of a world's regions per model (matching the pre-existing region_labels rationale), which would also resolve C4, C5, and C7 as a side effect of the same rewrite. This is not a bigger version of last round's C1/BC-4 fork — it's a bounded, mechanical redesign once the one question (does JudgeInput span one region or all of a world's regions?) is answered — but it should be answered deliberately, not patched around.

Cluster 4 — A real documentation-ownership decision (recommend: decide, write once)

C8, the out/ write-ownership contradiction across three documents.

The review does not decide any of Clusters 3–4's open questions. It records that the macro architecture is sound, the execution needs a second, more disciplined pass with the lesson generalized this time, and ADR-004's partitioning choice is the one item that needs a decision before more code gets written against it.
