World Model Judge — Design Review — Round 10

Before the two practice models are trained, twelve independent reviewers checked the plan for how they will be trained. They found twenty real problems. None of them is a result — nothing has been trained. They are holes in the plan that would have forced a builder to guess, or that would have let the pre-registered recipe be quietly changed. Several were confirmed by running code, not by argument.

Verdict

Verdict (after owner triage, 2026-09-28)
Do not build from the proposal as written

Nine Critical findings, every one accepted for fixing by the owner. P3-C06 and everything trained from the recipe stays blocked until the accepted fixes are written into the specs, test cases and one open, dated revision of prereg/recipe.md, and an independent fix-check confirms each one. In plain words: the plan was nearly right but had holes a builder would have had to guess through; fill the holes, have someone else check the fills, then build.

Method

  • 6 defect-class panels (A requirements coverage; B interface contracts; C structural soundness; D implementability; E integrity/anti-gaming; F runtime quality attribute), each run twice: calibrated (with review history) and blind (without), 12 reports, Sonnet, strict Round-10 criterion.
  • ~70 raw findings merged into 20 (R10-F01..F20). Verbatim quotes spot-checked against the files (ADR-J6 envelope, worlds ADR-W3 null actions, models ADR-M3 identical data, ADR-M5 non-publication residual, out/ gitignored, prereg.py:266, recipe batch_size 32) — all matched.
  • All 20 then re-checked by one fresh-context verifier that had not seen the panels' reasoning, told to look for reasons each was wrong: 20 CONFIRMED, 0 partial, 0 refuted.
  • Measurements run in this session (single thread, this environment — not the 4-core reference laptop):
    • one network call at a time: 11–14 µs; batched 200: ~0.7 µs per state.
    • gradient check on 50,000 examples: ~400–700 s (extrapolated from 32/256/2000); on 32: 0.4 s.
    • kicks over the full horizon: LV 4 crashes in 2,000 training-region runs; 17/300 with out-of-range kicks; 68/300 from out-region starts (0/300 there without kicks). Pendulum 0/300.
    • batched world step (same rk4_step, batch-aware derivative, np.sin/np.cos): bit-identical to the one-at-a-time step for both worlds; 25–100× faster.
    • np.sin/np.cos vs math.sin/math.cos: 0 mismatches over 2,000,000 values (NumPy 1.26.4) — must still be a permanent test, since it is platform-dependent.
  • Calibrated vs blind: the blind panels found the same core issues (freeze gaps, subsample ownership, out-of-range actions, β-NLL gradient, eval runtime). Blind-only: re-freezing before a judged run (Cb-1); unnamed reference machine (Db-9). Calibrated-only: freeze-file self-reference (C-5); gradient-check cost (D-8); β-NLL calibration effect (C-3). High overlap suggests few defects remain unfound in this scope.

The 10-minute Question (Owner Asked: Challenge It)

Where 600 s came from. NF-2 (approved, Must) says only "minutes rather than hours" and states no purpose. The 600 s figure was chosen by the tech spec (judge ADR-J6) to make "minutes" testable, sized on an estimate now shown wrong three times (per-region multiplier, network count, and now evaluation cost).

What it is for. Both runtime panels agree: re-runnability — anyone can re-run the whole judge on an ordinary laptop and check the verdict themselves. That is the essay's "independent institution" in miniature. The number itself is not sacred: 10 or 20 minutes serves the same purpose.

What the measurements say. Run as currently designed (models asked one state at a time), the whole run is ~10–11 minutes — over. If the 200 test runs step forward together (batched), it is ~4–5 minutes: training ~3–4 min, judging well under a minute. Batching gives bit-identical numbers.

Recommendation. Keep the whole run in minutes; write the purpose (re-runnability) into NF-2's plain-words line; record 600 s in ADR-J6 as a revisable target with a measured envelope, not a FLOP guess; batch the evaluation. The alternative — loosen to ~20 minutes and keep one-at-a-time calls — serves the purpose equally; it is the owner's choice.

Runtime

R10-F01 · Critical · Judging time never measured
ADR-J6 guessed "well under a minute" from a FLOP count. Measured: ~23M one-at-a-time network calls ≈ 4–5 min, plus the true-world runs.
Recommend: FIX — batch the rollouts across the 200 trials (a batched predict that must equal the one-at-a-time answer exactly); rewrite ADR-J6's envelope with measured numbers. Changes the model interface (MU-1/ADR-M1) — owner decision.
R10-F02 · Critical · Gradient check would take 7–10 minutes
The spec says "one full-batch pass"; on 50,000 examples that alone exceeds the budget. It only needs to prove the maths is right.
Recommend: FIX — pin a small fixed gradient-check batch (e.g. 64 examples, seeded).
R10-F20 · Important · One blended timing, unnamed machine
Pendulum networks train ~37% slower than predator-prey; the reference machine is a 4-core laptop, not this container.
Recommend: FIX — per-world figures, name the machine; TC-NF2-01 on reference hardware stays the real check.

Training Data

R10-F03 · Important · Who draws the 50,000-example sample is unstated
Specs require training data built once by the harness and shared by all networks (ensemble members "identical training data"; fixtures rebuild direct bit-identically).
Recommend: FIX — harness draws it once per world; every network gets the same one.
R10-F04 · Important · No seed names for four new random draws
The specifications require seed naming for every random draw (sample, stratified selection, kick timing, kick size). The collision class fixed this three times before.
Recommend: FIX — pin the purpose keys.
R10-F05 · Important · New numbers not machine-readable; batch_size 32 still pinned; "≈1/s" not exact; rate→per-step formula missing
All new configuration values must be machine-readable and tied to their purpose; the conversion from per-second to per-step is omitted.
Recommend: FIX — key lines for every new value; exact rate; p = rate × dt stated.
R10-F08 · Important · No rule for which kick examples to keep when more exist than the 25% cap (~20k–28k available vs 12,500)
The training data preparation step does not specify how to select kick examples when the pool is larger than the 25% limit.
Recommend: FIX — seeded shuffle, take first ⌈0.25·M⌉; refuse loudly on shortfall.
R10-F11 · Important · Batched world step has no bit-identity test
Measured bit-identical in this session, but platform-dependent. The batched stepping path must be held to the same determinism standard as single-step.
Recommend: FIX — new test, exact equality, and the batched path must call the same rk4_step.

Kicks (The Action Lever)

R10-F06 · Critical · The kick generator cannot produce out-of-range kicks
WD-5/TC-WD5-02 already require out-of-range kicks (and no world declares an action-axis out-region today). The current implementation has no such capability.
Recommend: FIX — generator takes the kick-size range as a parameter; declare how the out-of-range-kick test runs are formed per world.
R10-F07 · Critical (upgraded from Important by measurement) · Kicks crash predator-prey over full-length runs
4 of 2,000 training runs; 23% of out-region runs; 6% with out-of-range kicks. The current rule aborts the whole job on any crash, so the training data cannot be generated.
Recommend: FIX — re-measure and pick an LV kick size/rate with no crashes in every region, or a seeded per-run redraw with the discard count reported and a hard cap; owner decides.
R10-F09 · Critical · The "world's own drift" yardstick was measured with no kicks, but every test run now has kicks
Chart 2's "only the gap above the line is the model's fault" and the switch-step/trust-horizon cap would compare against the wrong yardstick.
Recommend: FIX — measure the drift benchmark with the same kick sequence applied to both twin runs.
R10-F10 · Important · Training has 25% kicks, testing ~0.2–2%
Same for both models, but unassessed. The asymmetry between training and testing conditions has not been examined for impact.
Recommend: FIX — disclose as a limit; report a quick sensitivity check at P3-C03.

Model A's Loss

R10-F12 · Critical · β-NLL has no written gradient
The network has no automatic differentiation; the plain loss was written out for exactly this reason. The β-NLL loss function lacks its analytical gradient specification, making implementation error-prone.
Recommend: FIX — per dimension, with w = σ^(2β) held constant: ∂L/∂μ = −w·(y−μ)/σ², ∂L/∂(log σ) = w·(1 − (y−μ)²/σ²); summed over dimensions, averaged over the batch; update recipe text.
R10-F13 · Important · The prediction's reasoning names the flaw β-NLL removes
prediction.md expects direct to be overconfident — the plain-loss pathology that the custom β-NLL loss is designed to correct. This reasoning should be reaffirmed or revised before any training begins.
Recommend: FIX — owner re-affirms or rewrites the reasoning now, before any training (allowed: nothing has been trained).

Fairness (Anti-Gaming)

R10-F14 · Critical · "Is 50,000 enough?" would be judged by whether the two models come out matched
The adequacy of the training sample size would be evaluated by comparing the two model outcomes — tuning a setting until the result looks right, which is exactly the goalpost-moving this project is designed to detect.
Recommend: FIX — pin an outcome-independent test before training (each model's own held-out loss vs a larger sample), never the between-model margin.

The Freeze Point

R10-F15 · Critical · The lock can be moved
A git tag moves silently; the FREEZE file is not itself certified; unclear which wins; the file cannot contain its own commit id.
Recommend: FIX — the freeze commit is the commit that first added prereg/FREEZE (git-derived, not chosen), certified like the other files; the tag is a label only.
R10-F16 · Critical · "Refuse a second freeze after a judged run" has nothing to check
Since unpublished runs leave no trace, re-freezing before a judged run is not refused at all. The mechanism described in the spec does not actually prevent the problematic scenario.
Recommend: FIX — FREEZE may be added exactly once, ever (a second add is refused by check_prereg from git history); disclose the remaining gap (informal fitting before the freeze) as a named limit.
R10-F17 · Important · The verdict would record the wrong commit
check_prereg returns the first-added commit; wiring at P6-C01 would happen before the freeze exists.
Recommend: FIX — return the freeze commit; build R10-5 before P6-C01.
R10-F18 · Important · The tests describe the old lock
TC-MU6-01/04 name first-added commits; no test covers the freeze mechanism itself.
Recommend: FIX — rewrite both; add freeze tests (one freeze ever; freeze precedes judging; certified FREEZE).
R10-F19 · Minor · Option (a)'s weight hashing is unspecified
Only matters if cached weights are chosen.
Recommend: DEFER — specify only if (a) is chosen.
