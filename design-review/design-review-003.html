World Model Judge — Design Review 003

Independent dual/blind re-scan of all seven specification documents. Verification that Round 2's high-priority fixes (EOM, chunk count, AST gate, NF-4 scan) hold under adversarial pressure-testing. Discovery of 12 new Critical and 14 new Important findings, dominated by a structural theme.

Verdict

Verdict
Do not build

This is the third consecutive "Do not build" verdict, with both good and sobering news. The two fixes Round 2 flagged as least trustworthy — the physics correction and the security mechanism — both held under independent re-derivation, term for term. The rest surfaced a large new defect population dominated by one recurring structural theme: six instances of "a metric needs keys (task, region, step) but the schema is missing one." Every enforcement mechanism introduced in Round 2 has a real gap: the NF-4 scan's pre-commit hook has no installation path; the AST gate has multiple evasion routes (alias indirection, getattr, exec); the TC-MU9-01 registry test is tautological. Most importantly, patching the specific instance a review names does not close the category the instance came from. A structural fix — one canonical multi-key schema shape and adversarial pressure-testing of enforcement mechanisms before marking them resolved — would likely close most of both families.

Executive Summary

Fourteen independent reviewers (seven defect-class panels, each run twice: once calibrated with prior-round knowledge, once fully blind with none) scanned all specifications under the methodology's strict dual/blind protocol, which triggers automatically at 2+ prior rounds.

The positive signal: both highest-priority verification targets held. Two independent reviewers each re-derived the double-pendulum equations from Euler–Lagrange and confirmed the v1.2 correction exactly, term for term. Two independent reviewers each recounted the implementation guide's chunk total from the dependency table and got 28 both times. These are the two critical passes this round was explicitly designed to run.

The pattern shift from Rounds 1–2: defects have moved from incompleteness (missing constants, unnamed edge cases) through inconsistency (the same fact defined differently in different places) to systematicity. Most new Critical findings are instances of one design principle applied inconsistently: "every fact keyed by (task, region, step) needs matching keys in the schema." Round 1 found it on Chart 1. Round 2 found it on Chart 2 and 3. Round 3 finds it on six more blocks. This is not six bugs; it is one rule that has never been applied systematically.

The confidence signal: thirteen of ~24 new findings were independently discovered by two or more of the fourteen reviewers with zero shared context between calibrated and blind runs — the methodology's strongest available confidence form.

New Findings — Critical (12)

NC-1 — NF-4's pre-commit hook has no described installation mechanism

E-calibrated, E-blind, A-calibrated (3 independent panels)

Git hooks live in .git/hooks/, which git clone never populates. No document names a pre-commit install step, a .githooks/ directory, or any wiring. implementation-guide.md P6-C02 treats the whole confidentiality scan as a runtime check (python -m wmj run), not a commit-time one — directly contradicting cross-cutting.md's own "pre-commit hook" framing. On a fresh clone, there is no hook to fail loudly with — the guarantee the v1.2 redesign exists to provide may simply never fire.

NC-2 — NF-4 scan never covers historical file-content blobs

E-calibrated, E-blind (2 independent panels)

Round 2 fixed the identical failure mode for commit messages — a term typed and removed remains visible via git log. The same reasoning applies to file content: a term committed and removed in the next commit is permanently visible via git log -p/git show. The current mechanism (git ls-files — current tree only) never checks it, leaving the more common channel open.

NC-3 — AST gate's dynamic-import coverage is a closed syntactic enumeration, evadable multiple ways

E-calibrated, E-blind, F1-blind (3 independent panels)

Alias indirection (import importlib as il; il.import_module(...)), getattr-indirection, and exec/eval on a constructed string all reach another package's code without matching any of the three enumerated Call-target shapes. This is the textbook LANGSEC failure for a denylist-of-known-shapes approach.

NC-4 — AST gate does not catch numpy.random.* legacy-global calls

F1-calibrated

numpy is the one module the judge is required to import and therefore cannot appear on a forbidden-import list. A call like numpy.random.rand() is an attribute-call on a legitimate import — none of the three checks would fire — yet ADR-002 rule 2 forbids exactly this, with this gate as its sole enforcement. The mechanism does not enforce the rule it claims to enforce.

NC-5 — TC-MU9-01 mechanism is structurally incapable of ever failing

F2-blind, F2-calibrated (2 independent panels)

The test stages, commits, and diffs a fixture file it fully controls end-to-end — the diff can only show the file it chose to write, providing zero information about a real contributor's changeset. Compounding: no mechanism explains how a new model file's register() call executes, given cross-cutting.md's own ban on __init__.py re-export mazes.

NC-6 — fx-brittle contradicts ADR-M4; its footprint has no relationship to the world region label (regression)

A-blind, C-blind, C-calibrated (3 independent panel-runs)

ADR-M4 states "each fixture wraps a copy of Model A (trained normally)" — true for others, false for fx-brittle, which requires from-scratch training on narrowed data. Worse: roughly half of what gets labelled "in-region" for fx-brittle (the untrained lower half) is territory the fixture never saw, directly undermining MU-3's whole point. Round 1 flagged the ambiguity; Round 2 "fixed" it by naming a split; Round 3 finds the split reveals a structural contradiction Round 2 didn't check for.

NC-7 / NC-8 — calibration and sharpness blocks lack per-task granularity

B-calibrated

ADR-J4 defines the 200-trial independent set per (model, world, region, task) — two tasks per world means two different trial sets — yet both blocks are flat, region-only, with no task key. sharpness's omission is worse: ADR-J4 explicitly reads "that region/task's mean 90%-interval width," a value the schema cannot supply per task.

NC-9 — climatology.per_task has no region field despite region-dependent definition

B-blind, C-blind (2 independent panels, unprompted convergence)

ADR-J5 states switch_step is measured against "the trial's region's curve" — divergence curves differ materially by region — yet the schema carries one scalar switch_step per task, structurally unable to hold two regions' different crossing points.

NC-10 — region_labels has three mutually inconsistent definitions with wrong cardinality

B-blind Critical, B-calibrated Important (2 independent panels)

worlds.md defines one categorical field; models.md's JSON shows two booleans plus unexplained axis: null; judge.md describes a third shape. None match. Separately, models.md's example shows one flat object, not an [n_trials]-shaped array — structurally incapable of saying "trial 47 was out-of-region" within a mixed batch judge.md requires.

NC-11 — Reporting's "computes no metric" invariant contradicted by Chart 3's binomial-SE formula

C-blind

reporting.md states twice that "every number on a chart comes from the verdict record" and reporting "never computes a metric" — but Chart 3's Y-error bars are sqrt(p(1-p)/n), a formula applied at render time to two Verdict inputs, not read verbatim. The analogy to exception-band inset is itself inaccurate — that inset draws a verbatim value, no formula.

NC-12 — Chart 2's log-scale Y-axis has no accommodation for guaranteed zero at step 0

D-blind, D-calibrated (2 independent panels)

error_vs_horizon's step-0 entry is trivially zero by the schema's own convention. log(0) is undefined; nothing in reporting.md's Chart 2 design says whether to start at step 1, floor the value, or use symlog.

What Prevents a Higher Score

The dominant pattern across all three rounds is now unambiguous: fixes are applied at the granularity of the finding, not the granularity of the design principle the finding violated. Every round finds a new instance of "a fact varies by (task, region, step) and some schema block doesn't carry the key it needs," and every round finds a new instance of "a fix for one attack/evasion left a structurally similar one uncovered."

Both are symptoms of the same root cause: verification of a fix means re-reading the fix's own text for internal consistency, not independently deriving, adversarially attacking, or exhaustively enumerating against the design principle the fix is supposed to instantiate. The two fixes that did survive independent pressure-testing this round (the EOM, the chunk count) are exactly the two assigned a from-scratch independent re-derivation rather than a re-read — which is strong evidence for what actually works here.

Recommendation for next action: A structural fix — one canonical multi-key schema shape used everywhere a fact varies by task/region/step, and a rule that any new enforcement mechanism gets an adversarial pressure-test (fresh derivation, evasion attempt, real-usage simulation) before being marked resolved — would likely close most of both families at once.
